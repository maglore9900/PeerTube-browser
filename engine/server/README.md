# Engine Server

Engine API for PeerTube Browser recommendations and video metadata. It reads `whitelist.db` without writing it, apart from the per-request video metadata write-back described under `/api/video` below, and it writes `subtitles.db`, the caption store it shares with the translate worker, described under `/internal/translate` and "Translate worker and its store contract". The Engine migrates `subtitles.db` at start (see Notes).
This service does not own user write/profile endpoints.

## What it does
- `/recommendations` recommendations.
- `/videos/{id}/similar` and `/videos/similar` read aliases.
- `/api/video` metadata for the video page, looked up by `id` (or `video_id`) and optional `host` (or `instance_domain`); a missing id answers 400 `Missing video id` and an unknown video 404 `Video not found`. It reads the DB row, then fetches live metadata from the source instance (the video detail `/api/v1/videos/{id}`, then its channel, each with an 8 s socket timeout and outside `db_lock`) and merges it over the row field by field: title, description, stats, tags, category, language, nsfw, duration and thumbnail. A field the source leaves absent, null or invalid keeps its DB value. Besides the title, channel, account, URL and stats keys, the response carries `tags` (list), `category`, `language`, `nsfw` (bool or null), `duration` (seconds or null) and `thumbnailUrl`. Category and language are stored as PeerTube ids and codes and answered as PeerTube's default labels (`data/peertube_labels.py`), or as the raw id or code when there is no default label. The route needs a `whitelist.db` migrated by `db/jobs/migrate-whitelist.py`, which adds `videos.language`; without it every request fails with `no such column: v.language`. The same migration rebuilds `video_embeddings` with its `ann_id` column, and the writer jobs (`sync-whitelist.py`, `build-video-embeddings.py` and the updater's merge) refuse a `whitelist.db` that lacks it. For the upgrade order see `DATA_BUILD.md`.
- `/api/video/refresh` gives the same answer in the same shape as `/api/video`. It is the route the Client proxies with its own budget; for that budget see `client/README.md`.
- Both video metadata routes write the merge back only when the instance's video detail call answered with a non-empty JSON object: the `videos` UPDATE (including `language`, `duration`, `thumbnail_url` and `last_checked_at`), the `channels` UPDATE when the row has a channel, and the reset of `instances.last_error`/`last_error_at`/`last_error_source`. The write runs under its own statement deadline, and a `sqlite3.OperationalError` is logged without failing the response. A detail call that failed, was unreachable or answered a malformed, empty or non-object body writes nothing, and the response then carries the DB values.
- `/internal/videos/resolve` internal read lookup for Client (`video_id/uuid + host`).
- `/internal/videos/metadata` internal metadata batch lookup for Client likes/profile. Entries are `{video_id, instance_domain}` or `{video_uuid, instance_domain}`, and one body may mix both; an entry with a non-empty `video_id` counts as the id form even when it also carries `video_uuid`. The uuid match is exact and case-sensitive, and where several videos share a `(video_uuid, instance_domain)` the lowest `video_id` wins. All entries are answered under a single `db_lock` hold, with one row per video in the order of the first entry that matches it. Unembedded videos are never returned. Videos at or over the error-count threshold are left out for both entry forms.
- `/internal/dislikes/centroids` clusters a set of disliked videos into up to four taste centroids for the Client; nothing is stored. It takes only `{video_id, instance_domain}` entries.
- `/internal/translate` answers a video's English caption cues for the Client's Translate overlay (`api/handlers/internal_translate.py`). It takes a POST body `{id, host}` and answers `{"state": "ready", "cues": [{start, end, text}]}` or `{"state": "none"}`.
  - **Request errors:** a body that does not read as JSON answers 400 with its message, a missing or blank `id`/`host` answers 400 `Missing id or host`, and a host `normalize_host` rejects answers 400 `Invalid host`.
  - **Checks before any fetch:** the video resolves as on `/api/video` (`resolve_video_row`, so the error-count threshold applies), and its `instance_domain` must not be on the active instance denylist. An unknown or denied video answers 404 `Video not found`, and neither the cache nor the instance is read.
  - **Cache:** `subtitles.db` holds one row per `(video_id, instance_domain, target_language)`, keyed on the resolved row's `video_id` and `instance_domain` with `target_language` `en` (`data/subtitles.py`). A row holds the state, the source (`instance` or `whisper`), the fetch time, the original track text, the cues as one JSON array, and the translate job columns `queued_at`, `started_at`, `finished_at`, `error`, `detected_language` and `attempts`. A `ready` row of either source is served. The route stores only `ready`; the job states `queued`, `running`, `failed` and `already_english` come from the translate worker. A key in a job state is a miss, so the instance is fetched on every view, and a `ready` store from the route replaces the job row, which ends that job. Every `none` is answered unstored, so a track added later can still change the answer. A cache read error counts as a miss, and a store error is logged and the answer stays `ready`.
  - **On a miss:** it reads `https://<instance_domain>/api/v1/videos/{uuid}/captions` (the row's `video_uuid`, else its `video_id`) and takes the first entry whose `language.id` is exactly `en`. The track path is that entry's `captionPath` when it is rooted, else the path of a `fileUrl` on the same host over https. No `en` entry, or neither usable path, answers `none`.
  - **Fetch bounds:** every fetch goes to `https://<instance_domain>` with no explicit port or userinfo, follows a redirect only to that same host over https, accepts only a 200, and stops at 2,000,000 bytes, an 8 s deadline per fetch, a 15 s budget across both fetches and a 4 s socket timeout. Any breach or network error answers `none`.
  - **Parsing:** the track must decode as UTF-8 and parse as strict WebVTT: a `WEBVTT` header line, then NOTE/STYLE/REGION blocks or cues with an optional identifier and a `[hh:]mm:ss.mmm --> [hh:]mm:ss.mmm` timing line. One bad block or an end before its start rejects the whole track as `none`. Cue text has its tags stripped and its entities decoded, empty cues are dropped, and cues are sorted by start then end.
- `/internal/events/ingest` temporary trusted bridge ingest for normalized events (`ENGINE_INGEST_MODE=bridge`). A successful ingest also runs the raw-event retention strip, at most once an hour: events older than `INTERACTION_RAW_RETENTION_DAYS` (default 30) lose their actor, payload and source instance but keep their ids (`docs/project/adr/0005-raw-event-retention-keeps-ids.md`). For setting the window see `DEPLOYMENT.md`.

## Translate worker and its store contract
`db/jobs/translate-worker.py` is a separate GPU process that generates English cues with Whisper into `subtitles.db`: `enqueue --id --host` queues one video under its canonical key, and `run` is the service that works the queue one job at a time. The Engine never imports it or faster-whisper, so the Engine runs on a machine without a GPU. Its bounds default to `SUBTITLE_MAX_DURATION`, `SUBTITLE_MAX_BYTES`, `SUBTITLE_QUEUE_CAP` and `SUBTITLE_MAX_CHUNK_SECONDS` in `api/server_config.py`. For the job lifecycle, start-up, bounds, pipeline, lock and log files and exit codes see `db/jobs/docs/TRANSLATE_WORKER.md`; for the service unit and install see `DEPLOYMENT.md`.

The store functions in `data/subtitles.py` are the contract a route reading or queuing jobs builds on:
- `enqueue_translate_job` returns `("queued", "queued")`, `("exists", <state>)` for a key in any state, or `("cap", None)` when the cap's number of jobs is already `queued`. It never overwrites a row.
- A job row moves `queued` → `running` and ends `ready` (source `whisper`, or `instance` when the instance gained an English track before the claim), `already_english` or `failed` with its text in `error`.
- While a job is `running`, the worker rewrites the row's whole `cues_json` after each chunk. Only `fetch_ready_subtitles` reads cues, and it reads `ready` rows alone, so no reader serves `running` cues yet.
- The worker beats the single row `translate_worker_heartbeat(id = 1, beat_at, pid)` every 5 s, idle or busy, with `beat_at` in ms, and stops beating when the serve loop stalls; the age of `beat_at` tells whether a worker is serving.

## Boundary Contract (Engine-side)
- Engine owns read/analytics APIs and internal read/ingest contracts.
- Engine does not own browser-facing write/profile routes (`/api/user-action`, `/api/user-profile/*`).
- Engine runtime must not depend on `engine/server/db/users.db` for recommendation ranking.
- Client backend integration with Engine must go through HTTP contracts, not direct Engine module or DB coupling.

## Notes
- Reads from `DEFAULT_DB_PATH` and FAISS index, and at start opens `DEFAULT_SUBTITLES_DB_PATH` (`engine/server/db/subtitles.db`), creating the file when missing. It switches the file to WAL, retrying a switch that races another opener until the 30 s busy timeout, then in one IMMEDIATE transaction creates the `subtitles` table and adds whatever is missing of the job columns, the `subtitles_state_queued_at` index and the `translate_worker_heartbeat` table, so a file from before the job columns upgrades in place. Similar, vector search and the random cache resolve FAISS ids through `video_embeddings.ann_id`, so the Engine needs a migrated `whitelist.db` and an index built on `ann_id`. At start, `assert_index_matches_embeddings` (`data/embedding_space.py`) refuses an index whose sidecar `id_source` is not `video_embeddings.ann_id`, and the Engine exits with `Index ids come from <source or <unset>> but readers resolve video_embeddings.ann_id. Rebuild the index with build-ann-index.py.` For the cutover (migrate, rebuild the index, start) see the one-time `ann_id` migration in `DATA_BUILD.md`.
- POST `/recommendations` and POST `/videos/similar` validate the client `likes` list the same way and answer 400 when it is too long or holds a malformed entry. For the limit and the error bodies see `engine/server/api/recommendations/docs/OVERVIEW.md`.
- The query parameter `mode` on POST `/recommendations` and POST `/videos/similar` picks the home feed: `recommendations` (the default when missing or empty), `trending`, `recent`, `random` or `popular`. It applies only to unseeded requests. A request carrying `id`/`uuid`/`vector`, and every `GET /videos/{id}/similar`, never reads it, so an invalid value there still gets the normal up-next. On an unseeded request an unknown value answers 400 `{"error":"Unknown mode","allowed":["recommendations","trending","recent","random","popular"]}`, and so does `mode=hot`; the frontend reads a `hot` link or stored choice as `trending` before it asks. The check runs before the random branch, so `random=1&mode=bogus` also answers 400. `mode=random` is the same as `random=1` (any value other than `0`), and `random=1` wins over `mode=trending|recent|popular`. Trending, popular and recent are global orders, the same for every visitor. They continue past the body's `exclude` list and apply the error threshold and serving moderation. Trending serves only videos ranked in `trending_ranks`, so it answers an empty page until the updater's trending stage, or `db/jobs/fetch-trending.py` run by hand, first fills that table (see `db/jobs/docs/UPDATER_WORKER.md`). For the orders and how they page see `engine/server/api/recommendations/docs/OVERVIEW.md`. Only the query `mode` is read, and a `mode` key in the body is only logged. The response does not echo the feed mode: the ordered feeds answer with an empty `seed`, and `seed.mode` stays the profile mode (`home`/`upnext`).
- `debug=1` on `/recommendations`, `/videos/similar` and `GET /videos/{id}/similar` works only when the Engine starts with `RECOMMENDATIONS_DEBUG` set to `1`, `true` or `yes`; otherwise it answers 403 `Debug mode is disabled`. For where to set it see `DEPLOYMENT.md` section 7.
- `seed=<int>` on `/recommendations?id=`, `/videos/similar` and `GET /videos/{id}/similar` makes an up-next draw reproducible: a non-negative integer returns the same page for the same pool. Without it, each up-next request draws a different page. A missing, negative or non-integer value gives a random draw, not a 400. The Client gateway does not forward it and answers 400 `Unknown query parameter: seed`, so it works only on requests sent straight to the Engine. For how the page is drawn see `engine/server/api/recommendations/docs/OVERVIEW.md`.
- `nsfw` on POST `/recommendations`, POST `/videos/similar`, `GET /videos/{id}/similar` and GET `/api/v1/search/videos` includes NSFW-flagged videos only for the exact value `1`, read without stripping (`_parse_include_nsfw` in `api/handlers/similar.py`). A missing or empty value, ` 1`, `true`, `yes`, `0` or any other value leaves them out. Only rows with `videos.nsfw = 1` are left out; NULL and `0` pass (`NSFW_ALLOWED_SQL` in `data/metadata.py`). The filter covers every feed mode (the recommendations mix including its like layer, trending, recent, random and popular), the `random=1` alias and the empty-mix fallback, up-next, the raw-vector route and search. Flagged rows are left out while each pool or page is built, so pages stay full; for how each pool refills see `engine/server/api/recommendations/docs/OVERVIEW.md`. The raw-vector route (`vector=`) is the exception: it drops flagged ANN hits without refilling, so its page can be short. `/api/video`, `/api/video/refresh` and `/internal/*` are never filtered.
- The Engine sends no CORS headers on any response, and OPTIONS answers a bare 204 (`docs/project/adr/0004-cors-opt-in-by-origin.md`).
- An unexpected failure answers a fixed 500 with no exception text: `Recommendations request failed` from the recommendations/similar routes, including any `ValueError` other than the three seed-resolution texts that answer 400, and `Event ingest failed` from `/internal/events/ingest`. On the recommendations/similar routes a query that runs past the statement deadline, such as a slow ordered-feed page, also answers this 500, not the 503 `Query time limit exceeded`. The exception goes to the Engine log, where `EngineJsonFormatter` adds a `traceback` key to any record that carries exception info. Under `LOG_FORMAT=text` the traceback ends the record's line, newline-escaped (see `LOG_FORMAT` in `DEPLOYMENT.md` section 2).
- Every request logs `[request.start]` "request started" first, with `ip`, `method`, `url` and, when the `User-Agent` header is non-empty, `user_agent`. It logs `[request.end]` "request finished" last, with `status` (the code sent, or `-` if none was sent) and integer `duration_ms`. Both are written by `SimilarHandler._run_request` in `api/handlers/similar.py`. Every record between them carries `request_id`. That id is the incoming `X-Request-ID` when it fully matches `[A-Za-z0-9._-]{1,64}` (`resolve_request_id` in `api/request_context.py`), and a generated 32-hex `uuid4().hex` otherwise, so a rejected value is never logged. The `[similar-server][<id>]` prefix holds the same id. A 503 statement timeout and its `[statement.timeout]` warning fall inside the start/end window. http.server's own errors (bad request line, unsupported method, timeout) log one `[http]` WARNING with `peer` and no start/end pair. For following one id across nginx, the Client and the Engine see the Triage section of `DEPLOYMENT.md`.
- Recommendation ranking does not depend on local users likes DB; likes, dislike
  centroids and the videos a paging client excludes are read from request-scoped client
  input. Ingested interaction events are aggregated into `interaction_signals`, which no
  feed order or returned row reads.
