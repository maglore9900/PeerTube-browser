# Frontend

Static web UI for PeerTube Browser. It renders recommendations and video pages
using data from the backend API. The client stays UI‑only: no database access and
no ranking logic.

## What it does
- Fetches Client-backend gateway routes (`/recommendations`, `/videos/similar`, `/api/v1/search/videos`, `/api/video`, `/api/channels`). The video page also reads the source PeerTube instance's API directly: the video metadata fallback, `/api/v1/config`, channels, similar-video view counts and comments.
- Renders the home feed, the feed of videos similar to one video (`?id=`), and the video page.
- The home feed has five modes: Recommendations, Trending, Recent, Random and Popular. A switcher of `[data-feed-mode]` buttons in a `role="group"` picks one, and the active button carries `aria-pressed="true"`. For what each mode orders by, see `engine/server/api/recommendations/docs/OVERVIEW.md`. Trending, Recent and Popular are shown in the Engine's order; only Random is shuffled.
- The mode in effect comes from the URL's `?mode=`, then the legacy `?random=` (any value other than `0` means Random), then the JSON object `{mode}` stored in `localStorage` under `feedParams:v1`, then Recommendations. An unknown value in the URL or in storage reads as Recommendations, except `hot`, which reads as Trending (`parseFeedMode`), so a `?mode=hot` link or a stored `hot` opens Trending instead of sending a mode the Engine answers with 400. Choosing a mode stores it, sets `?mode=` and reloads the feed from the first page. `?id=` views ignore the mode. "Back to recommended" links to `/?mode=recommendations`, so it does not land on the stored mode.
- `src/data/feed-params.ts` is the one module that reads the feed parameters and the NSFW setting from the URL and storage, persists them, and turns them into the Engine request's query (the feed parameters through `buildSimilarUrl` in `src/data/videos.ts`, the NSFW setting through `nsfwQuery`). Page code does not build feed or NSFW query parameters itself.
- The NSFW setting hides NSFW-flagged videos from every video list and is on by default. It is stored in `localStorage` under `nsfwFilter:v1` as `on` or `off`, apart from `feedParams:v1`, and does not follow a profile key to another browser. Only a stored `off` turns the filter off; a missing, corrupt or unreadable value means on, and when the write fails the choice still holds for the current page. Its only control is the "Hide NSFW videos" checkbox (`label.profile-nsfw`) in the home page's Profile modal, shown in the keyless, key-holding and just-issued-key states with no key needed; the video and search pages have no control of their own. Changing it reloads the home feed, and an older load that resolves after the newer one is discarded. Home feed requests in every mode, up-next (the home `?id=` view and the video page, through `buildSimilarUrl`) and search (`fetchSearchResults` in `src/data/search.ts`) send `nsfw=1` only while the filter is off, reading the setting each time a request is built. The Engine does the filtering; for what `nsfw=1` includes see `engine/server/README.md`.
- The feed page loads another batch when scrolling reaches the end of the rows fetched so far. Each batch excludes the 500 most recently shown videos, rows already shown are dropped, and paging ends for that page view after a batch that adds nothing or fails (`createFeedPager` in `src/data/videos.ts`). A reload starts over. In Trending, Recent and Popular the Engine continues its order after the excluded rows, so paging ends after about 500 shown rows, or sooner for a visitor with a profile key whose blocked or disliked rows are removed by the Client backend (see `client/README.md`).
- Without a profile key, keeps likes in the browser (`localLikes:v1`), written only after the Client backend accepted them. With a key, likes and dislikes live in the profile: on load each page moves any local likes into it (`POST /api/profile/likes/import`) and clears them once imported, and feed requests carry no likes.
- Shows the visitor's reaction: the video page's Like and Dislike buttons (read from `GET /api/profile/reaction` with a key), and a mark on feed, search and similar-video cards (the Client's `reaction` row field with a key, `localLikes:v1` without). The reaction data lives in `src/data/reactions.ts`.
- Home feed and search cards that have a video key carry Like, Dislike, Block channel and Block account buttons. Like and Dislike carry `aria-pressed`. Like works without a profile key and toggles between `like` and `undo_like`. Dislike and both Block buttons need a key. Without one they send no request and write "Disliking needs a profile. Create one from the Profile button." or "Blocking needs a profile. Create one from the Profile button." into the card's status line. A Block also dislikes the video. If that dislike fails, the card reads "Blocked <source>, but the dislike failed: <message>" and no cards are removed. Otherwise every loaded card from the same channel (`instance_domain` + `channel_id`) or account (`account_url`) is removed. A failed action, including a rejected profile key, shows its message in that card's status line. The button is disabled while the request runs and is re-enabled afterwards.
- On the home feed, Dislike removes the card and cannot be undone there. On search, which is not filtered by dislikes, Dislike toggles between `dislike` and `undo_dislike` and the card stays on the page with its mark, and a like replaces a dislike and the reverse. After a Block removes search cards, the next page is fetched if the end of the results is now on screen. "Showing N of M matched videos." keeps counting the rows fetched, including removed ones.
- Clips the video page's description to 4 lines. A "Show more"/"Show less" button (`#description-toggle`, with `aria-expanded`) appears only while the text is taller than 4 lines, and is re-checked when the width changes. The expanded state lasts for that page view only and is stored nowhere. The text is set with `textContent`.
- Shows the video's comments from its source instance, read-only, in `#comments-section` between the video details and "Similar videos". The browser fetches threads from `https://{host}/api/v1/videos/{id}/comment-threads?start=…&count=20&sort=-createdAt`, newest first, 20 per "Load more comments", which hides once every thread has arrived. "Show N replies" fetches that thread's reply tree once from `/comment-threads/{threadId}` and shows it 20 rows at a time ("Show more replies"), indented by depth; "Hide replies" collapses it and expanding again makes no new request. Only when the first batch has `total` 0 does the page ask `/api/v1/videos/{id}` whether comments are disabled.
- The comments heading reads "Comments (N)" after the first batch. An empty list shows "No comments yet."; a failed first request, disabled comments or no resolvable host/id show "Comments are unavailable on {host}." with a link to the original video. A failed "Load more" or reply load logs one `console.warn`, keeps what is already rendered and leaves the button enabled so a click retries; there is no inline error message. Remote text is set only as text: federated HTML is reduced to plain text with its line breaks kept, links are not clickable and Markdown is shown raw.
- The About page loads `src/about-analytics.ts`, which sends one `page_view` when the page loads and one `outbound_click` for each click on an `a[data-track-id]` link to `POST /api/analytics/event` on the Client API base. It sends with `navigator.sendBeacon` and falls back to a `fetch` with `keepalive` when `sendBeacon` is missing, returns false or throws. A failed send is dropped without any error shown to the visitor, and the click is never stopped from navigating. For what the route accepts and stores see `client/README.md`.

## Boundary Contract (Frontend-side)
- Frontend must use Client API base (`window.location.origin` or `VITE_CLIENT_API_BASE`) for Client and Engine data. The video page reads source PeerTube instances directly (see "What it does").
- Frontend must not use direct Engine API base or Engine internal endpoints.
- A `VITE_CLIENT_API_BASE` on another origin than the page works only when the Client backend lists the page's exact origin in `CLIENT_CORS_ORIGINS`; otherwise the browser blocks every API call. `npm run dev` always sets `VITE_CLIENT_API_BASE` (default `http://127.0.0.1:7172`, see `scripts/dev.mjs`), so the dev page is cross-origin. For the variable's syntax see `DEPLOYMENT.md` section 6.
- The About page's analytics events are cross-origin under `npm run dev` too. They reach the Client backend only when the page's origin is in `CLIENT_CORS_ORIGINS`, and even then a browser can drop a cross-origin beacon (see `docs/project/adr/0004-cors-opt-in-by-origin.md`), so dev counts are not reliable.

## Debug view
`/videos.html?debug=1` shows each row's ranking metrics. It needs the Engine to run with `RECOMMENDATIONS_DEBUG=1`; otherwise the page shows `Debug mode is disabled`. See `DEPLOYMENT.md` section 7.

## Build
```
npm install
npm run build
```
The served `dist/` holds only what the last `npm run build` produced, so changes to `src/` or the HTML pages, the feed mode switcher included, reach it only after a rebuild. `dist/` is committed and must equal a fresh build: `tests/active/test_frontend_dist.py` fails on a stale one, so commit the rebuilt `dist/` with the source change.

## Local About Overrides
- Default production source is `client/frontend/dev-pages/about.template.html`.
- Local developer overrides can be placed in:
  - `client/frontend/dev-pages/about.html`
- The build emits whichever source it used under `dist/dev-pages/`, and prod nginx serves it at `/about`, `/about/` and `/about.html`, the `dev-pages/about.html` override first and the template otherwise. For the nginx locations and the About visit log see `DEPLOYMENT.md` sections 3 and 6.
- An override must use root-absolute URLs (`/favicon.png`, `/src/videos.css`), because the same file is also served at `/about/`, where a relative URL resolves under `/about/`.
- The About page's only CSP is the server's `Content-Security-Policy` header, so an override must work under it.
- The template loads the analytics module with `<script type="module" src="/src/about-analytics.ts"></script>`. An override sends analytics events only if it carries the same tag with the same root-absolute `src`. Vite bundles the tag because the override is the `about` build input in `vite.config.ts`. An override without the tag sends nothing.
- To count clicks on an outbound link, give it `data-track-id="<id>"`, where the id fully matches `[a-z0-9_]{1,64}` (for example `about_github`). Only `http` and `https` links are counted; the Client backend rejects any other scheme. Opening a link with a middle click or from the context menu fires no `click` event, so it is not counted.
